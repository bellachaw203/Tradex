# Releases

Versioning, changelog generation, and cutting a release.

---

## How the version is decided

The bump is derived from the Conventional Commit messages since the last tag:

| Commits since the last tag | Bump |
| --- | --- |
| Any `!` marker or `BREAKING CHANGE:` footer | major |
| Any `feat:` | minor |
| Any `fix:` or `perf:` | patch |
| Only `chore`, `docs`, `test`, `ci`, `refactor`, `style` | **no release** |

This is why `pr-quality.yml` rejects a PR title that does not parse: a title of
"fixes stuff" produces no changelog entry, and a breaking change without the
`!` produces a minor bump for a change that breaks users.

### Pre-1.0 behaviour

While the version is `0.x`, a breaking change bumps the **minor**, not the
major — `0.1.0` → `0.2.0`. That is what the ecosystem expects and what cargo's
resolver assumes for `0.x` requirements. The script says so when it happens.

---

## Where the version lives

| File | Field |
| --- | --- |
| `Cargo.toml` | `[workspace.package] version` — every crate inherits it |
| `app/package.json` | `version` |
| `Cargo.lock`, `app/package-lock.json` | Refreshed automatically |

The Rust workspace uses `version.workspace = true` in each member, so the
version exists in exactly one place. `bump-version.sh` rewrites only the field
inside `[workspace.package]` — a naive find-and-replace would also rewrite
dependency version requirements.

## Cutting a release

### Preview first

```bash
gh workflow run release.yml -f dry_run=true
```

Computes the version and renders the changelog into the job summary. No tag, no
commit, no release.

Locally:

```bash
./scripts/ci/bump-version.sh --dry-run
./scripts/ci/changelog.sh 0.2.0
```

### Release

```bash
gh workflow run release.yml                    # derive the level from commits
gh workflow run release.yml -f level=minor     # force a level
```

The workflow then:

1. Computes the next version
2. Prepends the changelog section to `CHANGELOG.md`
3. Commits `chore(release): <version>`
4. Creates an annotated tag `v<version>` carrying the release notes
5. Pushes the commit and the tag
6. Builds the contracts and frontend from the tag
7. Publishes a GitHub Release with artifacts and checksums

### From a hand-pushed tag

```bash
git tag -a v1.2.0 -m "Release 1.2.0"
git push origin v1.2.0
```

The `push: tags: ['v*.*.*']` trigger builds and publishes for that tag, skipping
the bump and changelog-commit steps.

## Release artifacts

| Artifact | Contents |
| --- | --- |
| `tradex-contracts-<version>.tar.gz` | The five optimized `.wasm` files and their checksums |
| `tradex-frontend-<version>.tar.gz` | The static SPA bundle |
| `tradex-circuit-keys-<version>.tar.gz` | The Groth16 verifying keys the contracts were built against |
| `*.wasm` | Each contract individually |
| `SHA256SUMS-<version>.txt` | Checksums for everything above |

The verifying keys ship with the release because without them a third party
cannot reproduce or verify the build — the keys are compiled into the contract
wasm, so a different key produces a different, non-equivalent binary.

Verify a download:

```bash
gh release download v1.2.0
sha256sum -c SHA256SUMS-1.2.0.txt
```

## Changelog

`CHANGELOG.md` is generated by [`scripts/ci/changelog.sh`](../../scripts/ci/changelog.sh)
from commit messages — **edit the commits, not the file**. A hand-edit is
overwritten by the next release.

Sections, in order:

1. ⚠️ Breaking changes
2. ✨ Features (`feat`)
3. 🐛 Bug fixes (`fix`)
4. ⚡ Performance (`perf`)
5. ♻️ Refactoring (`refactor`)
6. 📚 Documentation (`docs`)
7. 📦 Build (`build`)
8. 🔧 CI/CD (`ci`)
9. ⏪ Reverts (`revert`)
10. 📊 Release details — commit count, diff link, contributors

`chore`, `test` and `style` commits are deliberately omitted: they describe work
on the repository, not changes to the software users run.

The generator is dependency-free — plain `git log` and shell. A release path is
worth keeping debuggable, and a supply-chain-sensitive repository does not need
a release toolchain pulled into CI just to format text.

## Deploying a release

Releases and deployments are separate on purpose. Publishing a release does not
deploy it.

```bash
gh workflow run cd.yml --ref v1.2.0 -f environment=production
```

Production requires reviewer approval before the job starts. See
[DEPLOYMENT.md](DEPLOYMENT.md).

## Troubleshooting

**"No release-worthy commits."** There were no `feat`, `fix`, `perf` or
breaking-change commits since the last tag. Either that is correct, or a PR
title was mis-typed. Force a level with `-f level=patch` if you need a release
regardless.

**The tag exists but there is no release.** The build or publish job failed
after tagging. Re-run the workflow from the tag: the `push: tags` trigger
handles it without re-bumping.

**Wrong version computed.** Check `git log $(git describe --tags --abbrev=0)..HEAD --oneline`
for a mis-typed prefix. Correct it with `--set`:

```bash
./scripts/ci/bump-version.sh --set 1.3.0
```

**Tag pushed but no downstream workflow ran.** Expected: pushes made with
`GITHUB_TOKEN` do not trigger workflows, to prevent recursion. Configure
`RELEASE_TOKEN` if you need that ([SECRETS.md](SECRETS.md)).
